# Revisão de segurança — 3 de outubro de 2026

Escopo: código atual, dependências instaladas, configurações locais e quatro consultas HEAD anônimas ao Supabase. Não houve alterações na aplicação, login com contas reais, escrita no banco ou execução de exploits de RCE. Foram adicionados somente testes de auditoria e este relatório.

## 1. Alta: redirecionamento externo após autenticação — confirmado

Local: `app/auth/callback/route.ts:7–14`.

O parâmetro `next` é concatenado com a origem sem validação. Um valor `@phishing.invalid/login` produz `https://expense.example@phishing.invalid/login`: o navegador interpreta `expense.example` como informação de usuário e o destino como `phishing.invalid`. Isso permite aproveitar um link com o domínio legítimo para enviar a vítima a uma página falsa depois do login.

Reprodução local: `node tests/security-review.mjs`. O teste executa a função real do callback com a troca do código simulada e confirma o host externo. Requer que a troca de código tenha sucesso; não permite inventar um código OAuth válido, nem comprova vazamento direto dos tokens.

Correção recomendada: aceitar somente caminhos relativos internos que comecem com `/`, rejeitar `//`, barras invertidas e credenciais, resolver a URL e verificar que sua origem permanece igual à origem confiável. Usar `/` como fallback. Restringir também as URLs de callback autorizadas no Supabase.

## 2. Crítica: versão do Next.js em faixas vulneráveis — confirmado pelo registro

Instalado: Next.js 16.3.1 e sharp 0.35.3. O `npm audit` identificou 18 pacotes afetados: 1 crítico, 13 altos, 3 moderados e 1 baixo. Isso não significa 18 caminhos exploráveis: dependências transitivas repetem alertas e diversas bibliotecas são usadas apenas por ferramentas.

Alertas principais:

- [RCE sem autenticação em servidores Windows](https://github.com/advisories/GHSA-p293-qw3h-jr36): Next.js 16.3.1 está na faixa afetada. A máquina desta revisão usa Windows e o projeto usa App Router sem Cache Components configurados. O sistema operacional e a exposição do servidor de produção não foram verificados.
- [RCE na otimização de AVIF](https://github.com/advisories/GHSA-2xp9-vwfh-vxw4): a versão instalada está na faixa afetada. Há uso de `next/image`, mas o arquivo observado é PNG fixo, sem upload público de imagens ou fontes remotas configuradas. O alerta não comprova que um atacante consegue fornecer AVIF para este projeto.
- [RCE em next/og ImageResponse](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j): versão afetada, porém não encontrei uso de `ImageResponse` no projeto; não há caminho identificado neste código.

O registro indicou Next.js 16.3.8 como atualização disponível para corrigir o conjunto de alertas. Recomendo atualizar Next.js e eslint-config-next de forma compatível, revisar sharp e dependências transitivas e repetir testes/build/audit. Não executar `npm audit fix --force` indiscriminadamente: a ferramenta sugeriu até regressões de versão major para ferramentas como shadcn e eslint-config-next.

Detalhes completos: `security/dependency-audit.json`.

## 3. SQL injection: nenhum caminho direto encontrado; funções SQL não auditadas

As consultas examinadas usam `.from`, `.eq`, `.gte`, `.lt`, `.insert`, `.update` e parâmetros de `.rpc`. Não encontrei SQL bruto concatenado, execução de SQL enviada pelo navegador ou filtros `.or` montados com entradas não confiáveis.

O teste local verificou que uma entrada com sintaxe SQL permanece um valor de filtro no SDK. Esse teste não demonstra a segurança de toda a API ou de funções SQL no servidor.

A implementação de `delete_board_cascade`, chamada em `components/expenses-dashboard.tsx:116`, não está no repositório. É necessário examinar seu corpo SQL, eventual SQL dinâmico, `SECURITY DEFINER`, `search_path`, privilégios de execução e validação do proprietário com `auth.uid()`. Não invoquei essa função porque ela exclui dados.

## 4. Acesso indevido entre usuários: verificação pendente de RLS

Diversas operações filtram apenas o ID da despesa, quadro ou grupo. Isso é aceitável somente se as políticas RLS do banco impuserem o proprietário autenticado, inclusive em `WITH CHECK` para inserções/atualizações e no vínculo entre despesas e quadros. Adicionar filtros de usuário no frontend não substitui RLS.

Consultas HEAD anônimas a `expenses`, `boards`, `salaries` e `reports` retornaram HTTP 200 com zero registros visíveis. Nenhum dado pessoal foi retornado. Isso é um resultado favorável, mas não prova que RLS está habilitada: tabelas vazias também produziriam esse resultado. Também não valida leitura/escrita cruzada entre dois usuários.

Não há migrações, políticas ou código SQL versionados neste repositório. Recomendo revisar as políticas no Supabase e testar SELECT, INSERT, UPDATE e DELETE com dois usuários de teste em ambiente isolado, incluindo associação de uma despesa a um quadro de outro usuário.

Referência: [RLS do Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).

## 5. Sessão e cabeçalhos: proteção adicional recomendada

`lib/supabase/session-config.ts:4` configura SameSite=Lax e persistência de 45 dias, mas não define `Secure`. Em produção HTTPS, habilitar Secure evita enviar os cookies em HTTP. A URL-base local usa HTTP; isso não é evidência de que produção também usa HTTP.

Não há CSP ou proteção de enquadramento configurada no `next.config.ts`. Recomendo uma CSP compatível com Next.js, Supabase e o worker de PDF, `frame-ancestors 'none'` ou política equivalente, `X-Content-Type-Options: nosniff` e uma política de referência adequada. Cabeçalhos da hospedagem e HSTS em produção não foram inspecionados.

Não recomendo simplesmente ativar HttpOnly neste projeto: o SDK de autenticação no navegador precisa acessar os cookies. Para usar HttpOnly, seria necessária uma arquitetura de autenticação exclusivamente no servidor. A sessão longa torna prevenção de XSS e revogação no logout especialmente relevantes.

Não encontrei `dangerouslySetInnerHTML`, `innerHTML` ou `eval` na aplicação. Os textos de despesas e mensagens aparecem via React, o que protege contra inserção direta de HTML nesse caminho. Isso não certifica dependências ou todos os fluxos futuros.

## 6. PDF, abuso de autenticação e configuração

- A extração carrega o arquivo inteiro e todas as páginas sem limite explícito de tamanho ou páginas. Um PDF excessivo pode travar a aba. Limitar tamanho, páginas, linhas e duração de processamento; validar o formato. A seleção `accept=application/pdf` é uma orientação de UI, não uma validação.
- O worker PDF vem de um CDN externo. Hospedá-lo localmente reduz a dependência de execução de código de terceiros e facilita uma CSP mais restrita. Não houve evidência de comprometimento do CDN.
- Limites de tentativas de login, CAPTCHA, bloqueio de senhas vazadas, MFA e reautenticação para troca de senha dependem das configurações do Supabase, que não foram inspecionadas. A verificação da senha atual no botão de troca é frontend; garantias desse tipo precisam ser impostas pelo serviço de autenticação.
- A chave pública configurada foi classificada localmente como `anon`, sem imprimir seu valor. Os arquivos `.env` não estão versionados no checkout atual. Não foi realizada uma varredura de todo o histórico Git. A defesa existente contra `sb_secret_` não detecta uma chave JWT legada com papel `service_role`; isso é uma lacuna preventiva, não um segredo exposto confirmado.

## Prioridade proposta

1. Atualizar Next.js e corrigir o redirecionamento do callback.
2. Auditar RLS e a função `delete_board_cascade` no Supabase.
3. Configurar Secure/HTTPS, proteção contra enquadramento e CSP compatível.
4. Limitar PDFs, revisar dependências transitivas e conferir controles de autenticação no Supabase.

Scripts adicionados: `tests/security-review.mjs` (provas locais com serviços simulados) e `tests/security-supabase-probe.mjs` (HEAD anônimo somente leitura). Ambos passaram no lint. Não foram executados ataques em produção.
